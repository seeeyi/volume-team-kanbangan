# Shared LED Volume Team workspace

Phase two adds approved-account login, shared workspaces, authenticated edit credits,
server-owned history, revision checks and live updates. The existing browser-only
board remains active while `dist/team-config.js` has `enabled: false`.

## Activate

1. Create a dedicated Supabase project. Run
   `supabase/migrations/001_team_workspace.sql` in its SQL editor.
2. In Authentication, disable new-user signups. Create approved email/password
   accounts for Si, Mitch and Ken using the dashboard. Deliver initial credentials
   privately; never commit them. Do not use a single shared team password.
3. Insert their Auth user UUIDs into `public.vp_team_members` using an admin SQL
   session: Si with role `admin`, Mitch and Ken with role `editor`. The app cannot
   add members or grant itself admin access. No email addresses belong in source.
4. Put the project URL and **publishable** key (or legacy anon key) into
   `dist/team-config.js`. Never use a service-role/secret key. Keep `enabled: false`
   until the schema and account access checks pass.
5. Set `enabled: true` and push to GitHub. Cloudflare Pages serves the same `dist`
   directory; no build is required. The Supabase SDK is loaded from esm.sh only
   when shared mode is enabled. A backend or SDK failure keeps shared mode locked
   rather than silently falling back to browser-only edits.
6. Si signs in and uses Account → Import local board for the team. Import creates
   a new shared workspace, leaving the browser copy intact. If the old board was
   edited at another address/device, export the backup there first, create a shared
   workspace here, then use Import backup to bring that chosen board over.
7. Test two signed-in browsers: move a card in one and verify it appears in the
   other. Try a simultaneous stale edit and verify it is rejected. Test an
   unapproved account and logged-out database access. Check history and sign-out.

## Behaviour

- Si creates/renames shared workspaces; all approved members edit all task owners.
- One atomic workspace save uses an expected revision. It never silently merges
  stale snapshots. A failed/uncertain save keeps an exportable attempted edit and
  requires review before further edits or sign-out.
- Credits and history are generated by database functions from `auth.uid()`.
  Client-submitted editor names, task stamps and imported history are not trusted.
- An external revision clears local undo history so undo cannot silently erase
  someone else's changes. Editors can still change an earlier task through a
  normal checked save.
- Realtime subscriptions update the active board; focus/online events and a
  30-second refresh provide a fallback. Incoming changes are deferred while a task
  or notes editor is open. Saving against a stale revision prompts review.
- Shared snapshots are not stored in the old local board keys. Auth sessions are
  persisted by the SDK for quick return visits. Focus rewards stay personal and
  local to the browser, separate from project progress.
- This iteration uses email/password login and admin-assisted account/password
  management. Self-service invitations/reset UI and member administration are
  not included.
- The original public repository contains the initial planning seed. Login
  protects new shared database records; it does not erase previously public source
  or Git history. Do not commit new live board data to the repository.

## Verification

`node tests/team-sync.cjs` exercises the frontend login/save integration with a
mocked auth transport. `tests/backend.mjs` runs the actual SQL against PGlite;
install `@electric-sql/pglite` or point `PGLITE_MODULE` at its module path.
The tests cover member/anonymous access, direct-write denial, admin permissions,
trusted attribution, stale revision rejection, invalid data rollback, local-data
preservation, undo, concurrent-save guarding and sign-out.

Live Supabase, realtime delivery and visual browser QA require the configured
deployment and have not been verified by these local tests.
